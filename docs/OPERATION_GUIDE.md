# StampFly Integrated Control — 段階的安全飛行手順

本書はオペレータ向けの飛行運用手順。セットアップと UI の詳細は
[../README.md](../README.md)、フェイルセーフの正典は
[PROTOCOL.md](PROTOCOL.md)「タイミング・フェイルセーフ(規範)」。
v2 の運用手順(モーター実験モード §11、ヨー較正・FF パイプライン §12、
ヨー角制御飛行 §13、軌道モード(円・往復・評価シーケンス)§14、
飛行後解析 §15、複数機モード §16)は本書後半にある。

**原則: 各フェーズの確認項目がすべて合格するまで、次のフェーズへ進まない。**
リスクの低い順(机上 → 機体電源 OFF での通信確認 → 地上確認 → 短時間ホバー →
本飛行)に進める。

---

## 1. 飛行前チェックリスト

- [ ] 2m×2m 以上の空間を確保(Position モードは MoCap 計測範囲内)
- [ ] 周囲に人・ペットがいない。壊れやすい物を片付けた
- [ ] バッテリー充電済み(UI の電圧表示で 3.5V 以上が目安。3.4V 未満は飛行不可)
- [ ] プロペラの損傷なし。プロペラガード装着(推奨)
- [ ] 機体は平らな床の中央に水平に置く
- [ ] PC のキーボードに手が届く位置にいる(**SPACE = 緊急停止**)
- [ ] 飛行は **release ビルド**のファームで行う(README §3)
- [ ] ヨー基準(MoCap/motion)を使う場合: 離陸ボタン付近のバッジが
      **「整列OK」**(EKF2 ヨー観測 fused ∧ |innov|<10° が 3s 継続)に
      なっていること(§13 プリフライト・インターロック参照。EKF2 制御
      est_mode=2 では成立まで離陸がブロックされる)
- [ ] ログ保存トグルは **START の 3 秒以上前に ON** にする(プリロールが
      アーム前区間を先頭に取り込む — 地上アンカー・電流バイアス復元に必須)

## 2. 緊急時の操作(最初に覚える)

下から順にエスカレーションする。**迷ったらまず SPACE**。

| レベル | 操作 | 効果 |
|---|---|---|
| 1 | UI の **STOP** ボタン(どのタブにもある) | CMD_STOP 送信 → 即時着陸。**全飛行状態で受理**(TAKEOFF/LANDING 中含む)。MOTOR_TEST 中はモーター停止 → WAIT。**複数機モードでは全機へ一斉送信** |
| 2 | **SPACE キー** | どこからでも(フォーカス位置に関わらず)即 STOP。**全タブで有効**。Experiment 中は CMD_MOTOR_STOP も送出し、スイープ/シーケンスも中断する。**複数機モードでは全機を一斉に止める**(機体単位の停止はない)。連打してよい |
| 3 | **機体の電源スイッチ OFF** | 最終手段。その高度から落下するため、低高度で機体に安全に近づける場合のみ |

補足(知っておくと落ち着いて対処できる):

- STOP 送信後 600ms 以内に着陸イベントがなければ、pc_server が**自動で再送**する
  (最大3回)。「応答がありません」警告が出ても機体側フェイルセーフが控えている。
- **PC・サーバ・リレーのどれが落ちても機体は自分で着陸する**: 飛行中に
  セットポイント(CMD_SETPOINT / CMD_POS_ERR、50Hz ハートビート)が
  200ms 途絶えると水平化、500ms で
  自律着陸(link_loss)に入る(§9 の表)。USB を抜く・サーバを強制終了する
  だけでも結果的に着陸する。
- OverG(衝突など >2.0g)を検出するとモータ即停止 → COMPLETE になる。復帰は
  機体を回収・静置してから UI の **Re-arm (RESET)**(推定高度 0.15m 未満でのみ受理)。

## 3. フェーズ0: 机上検証(リスク: なし、ハード不要)

```sh
# プロトコル実装の一致テスト
cd protocol && python3 -m pytest tests/ -q          # 全件 pass

# サーバのロジックテスト(フェイク serial/NatNet)
cd pc_server && .venv/bin/python -m pytest tests/ -q # 全件 pass

# ファームのコンパイル確認
~/.platformio/penv/bin/pio run -d firmware_stampfly -e release
~/.platformio/penv/bin/pio run -d firmware_relay -e release
```

すべて成功すること。venv が無ければ README §4.1 を先に実施する。

## 4. フェーズ1: 通信確認 — 機体電源 OFF(リスク: なし)

**機体の電源は OFF のまま**、PC⇔リレー区間だけを確認する。

1. リレーを USB で PC に接続し、pc_server を起動(README §5)、UI を開く。
2. ヘッダで機体プロファイルを選択し、リレーのポートを選んで「接続」。

確認項目:

- [ ] **シリアル**インジケータが緑
- [ ] **リレー**インジケータが緑(機体が OFF でも RLY_SET_TARGET の ACK は返る。
      黄のままなら README §7 のリレー欄を確認)
- [ ] コンソールに「リレーターゲット設定完了: <MAC> ch<N>」が出る
- [ ] **機体**インジケータは消灯のまま(電源 OFF なので正常)
- [ ] リレー統計 `relay ↑.. ↓.. err:0` が毎秒更新される(err が増えないこと)
- [ ] **STOP ボタンと SPACE キーを実際に押す**: コンソールに「CMD_STOP 送信」、
      しばらくして「CMD_STOP への応答がありません(再送上限到達)」警告
      —— 機体 OFF ではこれが**期待どおりの動作**。緊急停止の操作を体に覚えさせる

## 5. フェーズ2: 機体地上確認 — プロペラ回転なし(リスク: 低)

1. 機体を平らな床に置き、電源 ON。INIT → CALIBRATION → WAIT と進む間
   (数秒+静定 3 秒)は**機体を動かさない**(ジャイロ較正と AHRS リセット)。
2. UI で確認:

- [ ] **機体**インジケータが緑、状態バッジが **WAIT — 待機**
- [ ] 電圧が表示され 3.5V 以上(黄/赤なら充電してから)
- [ ] レイテンシが数値表示される(セットポイント往復が機能している証拠)
- [ ] 機体を**手で**ゆっくり傾けると姿勢バー(Roll/Pitch)が追従する
- [ ] 高度スライダを動かすと「高度(現在 vs 目標)」の目標マーカーが追従する
      (高度は離陸前から変更可能。これが離陸目標高度になる)

## 6. フェーズ3: 短時間ホバー(リスク: 中)

§1 のチェックリストを完了してから。**Posture タブ**で行う。

1. 高度スライダを 0.3m 程度に設定。Roll/Pitch はスライダ中央(0°)のまま。
2. ログ保存トグルを ON(後の較正・解析のため推奨)。
3. **START** → 確認ダイアログで OK → **1〜2 秒で STOP**(または SPACE)。

- [ ] まっすぐ離陸し、STOP で降下して着陸する
- [ ] **流れた方向(前後左右)をメモする**(§7 の較正に使う)
- [ ] 異常(片側に強く倒れる・異音)があれば即 SPACE → 電源 OFF し、
      プロペラ・モータを点検

問題なければ **5〜10 秒の通常ホバー**を行い、安定性とドリフト方向を再確認する。
複数回の離着陸(START→STOP→START→STOP)も正常に動くこと。

## 7. 機体プロファイル較正(角度バイアス)

機体には個体差があり、指令 0° でも一方向に流れる(ドリフトする)ことがある。
このドリフトを **PC 側プロファイルのバイアス**(`pc_server/config/airframes.json`
の `roll_bias_deg` / `pitch_bias_deg`)で打ち消す。ファームには入れない。

**考え方(ドリフト方向からの逆算)**: ホバー中に流れる方向 = 機体が実際に
傾いている方向。これを打ち消すには、**流れる方向と逆向きに傾ける指令**
(=バイアス)を常時加算する。必要量は流れの速さに応じて 0.5°〜2° 程度が目安。

**手順(Posture モードのスライダで「測る」)**:

1. バイアス 0 のプロファイルで 0.3m ホバーし、ドリフト方向と速さを観察する
   (5 秒程度。ログ ON 推奨)。
2. ホバーを続けたまま、**流れと逆方向に Roll/Pitch スライダを 0.5° 刻みで動かし、
   ドリフトが止まる値を探す**。符号に自信がなければ小さく振ってみて、
   悪化したら逆へ。バッテリー残量に注意し、必要なら着陸して再開する。
3. ドリフトが止まったときの**スライダ値がそのままバイアス値**。値を読み取って
   着陸(STOP)する。
4. UI ヘッダの**「編集」**で機体プロファイル編集を開き、該当プロファイルの
   `roll_bias_deg` / `pitch_bias_deg` にスライダ値を記入して**保存**
   (例: `-1.0` / `0.5`)。`notes` に測定日を残す。サーバの再起動は不要 ——
   保存と同時に選択中プロファイルのバイアスが再適用される(飛行中は
   選択中プロファイルの変更が拒否されるため、**必ず着陸後に保存**する)。
5. スライダ中央(0°)で再ホバーし、その場に留まることを確認。残るようなら
   1°→0.5°→0.25° と刻みを細かくして繰り返す。

検証・微調整のヒント:

- ログ(v4)の `roll_ref_rad`/`pitch_ref_rad` は**バイアス加算後**の送信値、
  `roll_bias_deg`/`pitch_bias_deg` は適用中バイアス(LOG_STRUCTURE.md)。
  引き算すればスライダ操作分が復元できる(deg 換算列は flight_log_viewer が
  読み込み時に自動生成する)。
- Position モード運用後の上級者向け確認: バイアスは **Posture の角度指令に
  のみ加算**され、Position(機上XY制御)では角度指令自体を送らない —
  定常オフセットは機上 XY PID の I 項が吸収する。そのため Position の安定
  ホバー中の機体計算指令(ログの `tlm_roll_ref_rad`/`tlm_pitch_ref_rad`)の
  定常値(deg 換算)が、そのまま機体差トリムの実測値になる。この値を
  プロファイルの `roll_bias_deg`/`pitch_bias_deg` に記入すれば Posture 飛行の
  較正に使える(記入後は必ず Posture の実飛行で確認する)。

## 8. フェーズ4: 本飛行

### 8.1 Posture モード(手動の姿勢・高度指令)

- Roll/Pitch スライダは飛行中のみ操作可。**小さく動かして必ず中央に戻す**
  (「中央に戻す」ボタン)。サーバ側でスルーレート 30°/s に制限されるが、
  指令を出しっぱなしにすれば機体は流れ続ける。
- 高度スライダは 0.1–1.0m。変更は 0.3m/s に制限されて反映される。
- 着陸は STOP。最大飛行時間 120 秒で自動着陸する(§9)。

### 8.2 Position モード(MoCap による位置保持)

前提: Motive/NatNet 設定済み(README §4.3)。

1. **離陸前に** Position タブで確認:
   - [ ] MoCap インジケータが「受信中」(緑)
   - [ ] 座標表示と XY プロットが、機体を手で動かすと追従する
   - [ ] 値が制御座標系として妥当(原点・軸方向が想定どおり)
2. 目標を「**この場で**」プリセットにする(現在位置 XY を目標化。
   離陸直後の横移動を防ぐ)。目標 Z は 0.3m 程度から。
3. **START**(MoCap が新鮮でないと拒否される)。
4. 安定したら目標 X/Y を **0.1〜0.2m 刻み**で動かして追従を確認。
   「原点」プリセットで (0,0) へ戻せる。
5. 着陸は STOP。MoCap が 300ms 途絶えると水平固定+警告、2 秒で自動着陸する(§9)。

#### 8.2.1 機上XY制御(CMD_POS_ERR)— Position/Multi の唯一の XY 経路(v2.2)

Position / Multi の XY 位置ループは**機上XY制御のみ**である:
PC は位置誤差(目標 − フィルタ後位置)を CMD_POS_ERR で 50Hz 送信し、
**機体側が自身のヨー推定で誤差を機体座標系へ回転(ヨー回転補償)して
XY PID を回す**。任意ヨー角での位置保持が原理上可能になる。ゲインは
ファーム `config.hpp` の `pos_*`(旧 PC 側実績値と同値で初期化。変更は
再書き込み)。機体側で計算された roll/pitch 指令は UI の「機体計算指令」
表示とログの `tlm_roll_ref_rad`/`tlm_pitch_ref_rad` に現れる。

(旧 v2.1 の XY 指令モード選択 `xy_command_mode` と PC 側 XY PID 経路
(`"pc"`)は v2.2 で削除された。`control.json` に該当キーは存在しない。)

**互換性**: 機体ファームの再書き込みが必須(CMD_POS_ERR 0x24 対応ビルド)。
旧ファームは 0x24 を無応答で破棄するため、離陸してもセットポイント途絶
扱いとなり 500ms でリンク喪失フェイルセーフ(reason=8 link_loss)の
自動着陸になる。リレーファームは型レンジ(0x10–0x2F)で中継するため
再書き込み不要。

初飛行前チェック(必須):

0. 機体ファームが CMD_POS_ERR 対応ビルドであることを確認する
   (未対応だと START 直後に reason=8 で自動着陸する)。
0.5. **座標マッピングと機上XY制御の整合(2026-07 自動化)**: 機上XY制御の
   符号規約はレガシーマッピング(既定・鏡映)で実証されている。設定タブで
   右手系マッピング(Y符号反転)を適用した場合、pc_server が送信境界で
   `err_y`・診断方位角を自動反転してレガシー相当に変換する(設定タブに
   「自動変換されます」と表示される)。軸入れ替えを含むマッピングは変換
   対応外で、XY_ERR_VALID が立たず位置制御飛行は無効化される(警告表示)。
   **クイック較正(Yaw 0)の機首方位は、これまで正常に飛行できていた
   向きを維持すること** — XY制御の回転整合は較正時の機首方位に依存し、
   自動変換は「従来と同じ較正手順」を前提に従来挙動を厳密に復元する。
   なお右手系では円軌道の CW/CCW ラベルが物理回転方向と一致するようになる
   (レガシー鏡映では画面表示と物理が逆だった)。
1. **フレーム整合の地上検証(符号)**: 機体を手で +90° 回し、ログの
   `mocap_heading_deg`(MoCap 実測、制御座標系)と `tlm_yaw_est_rad`
   (機体推定)が**同方向に**変化することを確認する。逆方向なら
   ファーム `config.hpp` の `pos_ctrl_yaw_sign` を -1 にして再書き込み。
   この検証は UI の **Settings タブ**のライブプレビューでも行える
   (正解Yaw と機体ヨー推定の差をリアルタイム表示。マッピングの軸・符号・
   ヨーオフセットは同タブで調整・保存できる。地上限定)。記録用の正解ヨーは
   `mocap_yaw_true_deg` 列(符号/オフセット/フリップ補正済み)を参照する。
2. **ヨー0°基準の整合(オフセット)**: 機体推定ヨーの 0° 基準は
   推定モードで異なることに注意:
   - est=EKF(`est_mode=1`、FF 適用後の既定): 基準は「Yaw 0」取得時の
     機首方位(NVS 永続化、再起動をまたいで維持)。**飛ぶ前に
     機首を制御座標系 +X へ向けて「Yaw 0」を取得(再取得)する**こと
     (Yaw 0 は共通モニタ列のクイック較正カードから全モードで押せる。
     FF 一時 off→復元→アンカー再取得まで自動で行うため、
     FF 適用済みのままワンクリックで再取得できる)。
   - est=Madgwick(`est_mode=0`): ヨーは WAIT 静定時と START 直前に
     リセットされるため、基準は **START 時点の機首方位**。START の際に
     機首を制御座標系 +X へ向けておく。
   - **絶対値チェック**: 離陸前に `tlm_yaw_est_rad`(est=0 なら `tlm_yaw_rad`)と
     `mocap_heading_deg` を比較し、定常オフセットが大きい(目安 ±15°超)
     場合は飛行しない(項目1 は符号のみの検証でオフセットは検出できない)。
3. 初回はヨー制御 OFF・ホバリングのみで位置保持品質を確認し、
   問題なければヨー角を段階的に付与する(§13 の段階手順に準ずる)。

補足: 機上XY制御では機体差トリムバイアス(プロファイルの roll/pitch
バイアス)は送信されず、機上 XY PID の I 項が定常オフセットを吸収する
(§7 の検証ヒント参照)。

### 8.3 終了手順

1. STOP → 着陸と WAIT 復帰を確認
2. ログ保存トグル OFF(ファイルが閉じられる)
3. UI で「切断」→ 機体の電源 OFF → バッテリーを外して保管

## 9. フェイルセーフ一覧(PROTOCOL.md より転記)

正典は [PROTOCOL.md](PROTOCOL.md)。PC 側閾値の実効値は
`pc_server/config/server.json`(`failsafe` 節)、ファーム側は
`firmware_stampfly/src/config.hpp`。

| 条件 | 動作 | 実装場所 |
|---|---|---|
| セットポイント(CMD_SETPOINT / CMD_POS_ERR)途絶 >200ms(飛行中) | roll/pitch を水平へ、alt_ref 維持。**ヨー制御中なら途絶時点の推定ヨー角をラッチして保持**(v2) | ファーム |
| セットポイント途絶 >500ms(飛行中) | LANDING へ遷移(reason=8 link_loss)。着陸中のヨーはレートダンピングのみ | ファーム |
| EKF 不健全(磁気更新凍結 ffg bit5 / アンカー無効 / FF無効)で est_mode=EKF(v2) | ヨー角制御を止めてレートダンピングに縮退。ffg / ff_status で UI に通知(§13) | ファーム |
| CMD_MOTOR_RUN 途絶 >1.5s(MOTOR_TEST 中)(v2) | モーター自動停止 | ファーム |
| 低電圧(<3.34V、20Hz×5サンプル連続 ≈0.25s) | 飛行中: LANDING(reason=4)。WAIT: START拒否(reason=5) | ファーム |
| OverG(>2.0g) | モータ即停止 → COMPLETE(reason=7)。CMD_RESETでのみ復帰 | ファーム |
| 最大飛行時間 120s | LANDING(reason=3) | ファーム |
| MoCap 途絶 >300ms(Position/Multiモード) | setpoint を水平に固定+UI警告(円軌道中は軌道位相・接線ヨー目標も凍結。Multi は機体ごとに判定) | pc_server |
| MoCap 途絶 >2s(Position/Multiモード) | CMD_STOP 送信(自動着陸)。円軌道中も同一。Multi は**当該機のみ** | pc_server |
| MoCap データ無効 >0.5s(Position/Multiモード。受信はあるがトラッキング喪失/外れ値/低信頼度が続く) | setpoint は水平固定のまま+UI警告(MoCap インジケータは「受信中(位置無効)」黄) | pc_server |
| MoCap データ無効 >2s(Position/Multiモード) | CMD_STOP 送信(自動着陸)。Multi は**当該機のみ**。完全途絶中は上の途絶ポリシーが優先 | pc_server |
| XY 位置誤差 >1.0m が 1.0s 継続(flying+閉ループ中) | 発散とみなし CMD_STOP(自動着陸)。RB 取り違え・偽データ追従の最終防衛線(v2 では Multi のみ→単機にも適用) | pc_server |
| STOP 送信後 600ms 以内に LANDING/WAIT イベントなし | CMD_STOP 再送(最大3回)+UI警告 | pc_server |
| シリアル切断 | UI赤色警告(機体側は上記リンク喪失で自律着陸。MOTOR_TEST 中は CMD_MOTOR_RUN 途絶停止) | pc_server |

このほか UI/サーバ/ファームの三層で指令クランプがかかる
(UI ±5°・0.1–1.0m・ヨー±180° / サーバ ±10°+30°/s・0.1–1.2m+0.3m/s・
ヨー±180°+45°/s / ファーム ±30°・0.05–1.5m・ヨーレート±0.5rad/s。
ARCHITECTURE.md「安全クランプ(多層)」)。

## 10. よくある問題(飛行時)

| 症状 | 対処 |
|---|---|
| START しても離陸しない | 状態バッジを確認。WAIT 以外では受理されない。「離陸拒否: START_REJECTED_…」がコンソールに出ていれば理由(低電圧/未準備)を解消。実験モード中は離陸不可(§11) |
| ホバーが一方向に流れる | §7 のバイアス較正。較正済みなら床の傾き・プロペラ損傷・気流を疑う |
| 飛行中に勝手に着陸した | コンソールのイベント(reason)を確認: link_loss=電波/USB、low_voltage=充電、max_flight_time=仕様(120s) |
| COMPLETE から動かない | OverG 後。機体を回収・静置(高度 0.15m 未満)して Re-arm (RESET) |
| Position で警告「MoCap 途絶」 | マーカーの隠れ・計測範囲外。頻発するなら Motive のカメラ配置と `control.json` のフィルタ設定を見直す |
| MoCap が「受信中(位置無効)」(黄) | フレームは届いているがトラッキング喪失/外れ値で位置が使えない状態。フィルタは連続外れ値から自動再シードするため通常は数秒で復帰する。復帰しない場合は Motive のリジッドボディ追跡(マーカー隠れ・反射)を確認。無効のままの START は拒否され、飛行中に続くと 0.5s で警告・2s で自動着陸(§9) |

# v2 運用手順(実験モード・ヨー較正・ヨー制御飛行・円軌道・飛行後解析)

## 11. モーター実験モード(Experiment)の安全手順

Experiment タブは**ベンチ実験専用**で、機体はプロペラを回したまま飛ばない
(MOTOR_TEST 状態。飛行制御 PID・ミキサは動かない)。プロペラ回転を伴うため、
**機体の固定が最優先の安全策**である。

手順(この順番を守る):

1. **機体を固定する**: プロペラを外せない実験(スイープ)は、機体を
   テープ等で作業台へ確実に固定する。周囲に紙・軽量物を置かない。
2. 機体電源 ON → WAIT を確認し、UI で接続する。
3. **Experiment タブへ切替**: pc_server が 50Hz セットポイント送信を停止し、
   CMD_MODE(1) を送って機体を MOTOR_TEST に遷移させる。バッジが「有効」に
   なることを確認(「未有効」のままなら「実験モードを有効化」を押す。
   機体が WAIT 以外だと ACK bad_state で拒否される)。
4. **「機体をテープで確実に固定したことを確認した」チェックを ON** にする
   (これを入れるまでモーター/スイープ/シーケンスの開始ボタンは無効)。
5. モーターテスト: duty ボタン(0.1〜1.0)を選んで Start。
   **duty 0.6 以上は「高出力許可」チェックが別途必要**(機体固定を再確認)。
   duty はソフトスタート 2.0 duty/s でランプする。
6. 停止は **Stop ボタンまたは SPACE**(Experiment 中の SPACE は
   CMD_MOTOR_STOP+CMD_STOP を送出)。

LED 表示: MOTOR_TEST 中は橙点滅。計測(explog 記録)中は**マゼンタ常灯**になり、
**LED がマゼンタに変わった瞬間が計測開始(t_s=0)= スマホ動画のカット位置**
(同期規約。LED の全状態一覧は [LED_STATES.md](LED_STATES.md))。

多層の自動保護(操作ミス・リンク断に対する備え):

- PC は CMD_MOTOR_RUN を 0.4s 周期で再送(キープアライブ)し、機体は
  **1.5s 途絶でモーターを自動停止**する(USB を抜いても止まる)。
- スイープは **電池電圧 <3.0V(過放電防止)/ 電流 >12A / TLM_EXP 2s 途絶**で
  自動中断する(収集済みデータは保存される)。
- 加算性シーケンスは各スイープ前に**電池ガード(vbat ≥ 3.5V、UI で変更可)**で
  ブロックし、不足時は「電池交換 → 再開」の明示操作を要求する。
  スイープ間に冷却 10s を挟む。
- 実験を終えて Posture/Position タブへ戻ると、モーター停止確認 →
  CMD_MODE(0) → WAIT 復帰 → 50Hz 送信再開、の順で自動処理される。

## 12. ヨー較正・FF パイプライン(一連の手順)

ヨー角制御飛行(§13)の前提となる較正の全手順。詳細仕様は
[FF_PIPELINE.md](FF_PIPELINE.md)。スイープ・3D磁気・Accel6・地磁気などの
パネル操作は Experiment タブで行う(§11 の安全手順を先に完了しておく)。
**クイック較正(Attitude 0 / Yaw 0)だけは共通モニタ列のカードにあり、
Experiment に入らなくても全モードで実行できる**(v2.2。地上でのみ受理。
Multi モード中はカード内で対象機体を選ぶ)。

1. **地磁気プロファイル**: 「地磁気」パネルで都道府県を選択 → 保存+機体へ
   CMD_GEOMAG_SET 送信される。
2. **加速度6面較正(推奨)**: 「Accel6」パネルで6面(x±/y±/z±)を各面静置して
   キャプチャ(約1秒平均)→ 適用(適用時に姿勢参照がリセットされる)。
   必要なら「Attitude 0」で治具上のマウントオフセットも設定する。
3. **3D磁気較正**: 「3D磁気キャリブレーション」開始 → **機体をあらゆる向きに
   ゆっくり回す**(最低 80 サンプル、上限 6000)→ 停止 → Fit → 適用。
   適用で機体 NVS に書き込まれ、PC 側にも `pc_server/config/mag3d_calibration.json`
   として保存される(以後のスイープ CSV の b*_cor 計算に使用)。
   **注意: mag3d を適用/クリアすると機体側で FF は自動無効化(ff_mode=0)される**。
   FF 適用済みなら再抽出・再適用が必要。
4. **ヨーゼロ(任意)**: 現在の機首方位を 0° 基準にするなら共通モニタ列の
   クイック較正カードで「Yaw 0」。ワンクリックの自動シーケンスで、
   **FF 適用済みでもそのまま押してよい**
   (サーバが FF 一時 off → ヨーゼロ設定 → FF 復元 → アンカー再取得まで
   自動実行する)。飛行中・モーター回転中・実験計測中・スイープ/シーケンス
   実行中は拒否されるので、先に着陸/停止してから押す。
5. **スイープ 8 本**: FF 抽出には次の 8 本(16 ファイル)が必要。
   - **全機(FL+FR+RL+RR)× 4 姿勢**: 機体の向きを変えて 4 本。各ランの
     notes の「方位」に `Yaw=0°` / `Yaw=90°` / `Yaw=±180°` / `Yaw=-90°` のように
     **4 種の異なる姿勢**を必ず記録する(抽出時に検証される)。
   - **単機 FL / FR / RL / RR × 各 1 本**: 加算性シーケンス(自動 4 本)を使うと
     電池ガード・冷却込みで実行できる。
   - パターンは往復(updown、既定)推奨。中断ラン(aborted)は抽出に使えない。
6. **フォルダ整理**: `pc_server/data/sweep_results/` の直下にサブフォルダ
   (例 `DroneTest_20260629/`)を作り、8 本ぶんの
   `sweep_*_samples.csv` + `sweep_*_meta.json` を移動する(UI の抽出は
   フォルダ選択式)。
7. **FF 抽出**: 「FFプロファイル」パネルでフォルダを選び「抽出実行」
   (内部で `data_analysis/make_ff_profile.py` をサブプロセス実行、120s
   タイムアウト)。警告(mag3d 不一致等)が出たら内容を確認する。
   CLI で直接実行してもよい:
   `cd data_analysis && .venv/bin/python make_ff_profile.py --folder <フォルダ名>`。
8. **FF 適用**: プロファイルを選び、ff=方式B・est=EKF(既定)で「適用」。
   CMD_FF_BEGIN→LUT×n→MOT×4→AUX→COMMIT(CRC-32 照合)の分割転送と
   読み戻し検証が自動で行われ、成功すると「適用・CRC照合OK」+適用中バナーに
   なる。**「mag3d が取得時と一致しません」警告が出た場合は原則スイープ再取得**
   (force 適用は係数が現在の磁気較正空間と不整合になることを理解した上で)。
9. **ヨー評価**: §13 の Phase 0(ヨー制御 OFF 飛行)でログを取り、§15 の
   flight_log_viewer で 4 系統比較・EKF 診断を確認する。

## 13. ヨー角制御飛行の段階手順

ヨー角制御(CMD_SETPOINT flags bit1)は v2 の新機能であり、
**必ず OFF での検証飛行(Phase 0)から始める**。

### Phase 0: ヨー制御 OFF で飛行し、推定の符号と健全性を確認する

1. ヨー角制御トグルは **OFF のまま**(機体は V1 と同一のレートダンピングのみ)、
   ログ保存 ON で通常のホバー飛行を行う(§6/§8)。飛行中に機体を手で回す必要は
   ない — 離着陸時の自然なヨー運動で十分。可能なら Position モードで飛ぶと
   MoCap ヨー真値も同時記録される。
2. 着陸後、flight_log_viewer(§15)で確認:
   - **ヨー比較図**(`10_yaw_comparison.png`): `tlm_yaw_rad`(Madgwick)と
     `tlm_yaw_est_rad`(EKF)が**同じ向き・同じ量で動いている**こと
     (符号が逆なら較正・設定を疑い、ヨー制御 ON に進まない)。
   - **系統別統計**(`summary.txt` / `index.html`): ジャイロ積算・MoCap 真値を
     含む全系統の対基準(MoCap があれば MoCap、無ければ Madgwick)RMS・
     最大誤差・ドリフト率 [°/min] が表になる。EKF のドリフト率が
     ジャイロ積算より十分小さいこと。
   - **EKF 診断**(`12_ekf_diagnostics.png`)で NIS が定常(概ね <5.99)で、
     ゲート発火(ffg)が散発以上に出ていないこと。
3. 飛行中は UI のヨー推定モニタ(Madgwick / EKF / ジャイロ積算の数値と
   EKF 健全性バッジ)でも大まかな一致を確認できる。

### Phase 1: ヨー角制御 ON(低ゲインから)

1. FF プロファイル適用済み(§12)・EKF バッジが「EKF OK」であることを確認し、
   ホバー安定後に**ヨー角制御トグルを ON** にする(ON 時に FF 未適用だと
   「FF未適用」警告バッジが出る。飛行は可能だがモーター電流による磁気干渉を
   受けるため推奨しない)。
2. ヨースライダを **±10〜20° だけ**動かし、行き過ぎ・振動なく回頭して
   保持することを確認する。指令はサーバ側で最短経路 45°/s に整形され、
   機体側はヨーレート ±0.5 rad/s にクランプされる(PC 側スルー 45°/s=0.79rad/s
   より小さいため、大きなヨー指令変更のランプ中は追従が一時的に遅れる)。
3. 問題があれば即着陸。ヨー角 PID の初期ゲイン
   (`firmware_stampfly/src/config.hpp` の `yaw_angle`: kp=3.0, ki=0.3
   (ti=10.0 表現), kd=0.0)は**未飛行の初期値(要飛行チューニング)**であり、
   振動するなら kp を下げて再ビルドする。
4. 徐々に大きな回頭(±90°、±180°)へ進める。±180° 指令は wrap により
   どちら回りにもなり得ることに留意する。

### EKF 不健全時の縮退挙動(知っておくこと)

- est=EKF で飛行中に EKF が不健全(磁気更新凍結 ffg bit5 / アンカー無効 /
  FF 無効)になると、機体は**ヨー角制御を自動で止めてレートダンピングに縮退**
  する(飛行中のヨーソース切替による指令段差を作らないため)。機体は落ちないが
  **ヨーは保持されなくなる**(ゆっくり流れる)。UI の EKF バッジが「EKF注意」に
  変わり、ffg / FF状態表示で原因を確認できる。
- 縮退が起きたら回頭操作をやめ、必要なら着陸する。回復は着陸後に
  アンカー再取得(モーター停止中のみ受理)や FF 再適用で行う。
- CMD_SETPOINT 途絶(>200ms)時は、ヨー制御中なら**途絶時点の推定ヨー角を
  ラッチして保持**する(0° への回頭はしない)。>500ms で自律着陸(既存)。

### プリフライト・インターロック(EKF2 ヨー基準整列。2026-07-31 追加)

7/31 の両フライトで「EKF2 のヨー観測が離陸前から全棄却(融合 0%)のまま
飛行した」事故を受け、サーバ側に離陸ゲートを新設した
(FLIGHT_ANALYSIS_20260731.md §7-B-2)。

- **発動条件**: ヨー基準ソース(磁気オートチューンカード)が `off` 以外。
- **整列条件**: `ekf2_status` bit1(fused)=1 **かつ** |innov| < 10° が
  **3 秒連続**成立(テレメトリ途絶・不成立フレームで計時リセット)。
- **est_mode=2(EKF2 制御)**: 整列成立まで **START をサーバ側でブロック**。
  UI の離陸ボタン付近のバッジ(整列OK / 整列待ち / 融合なし / 再捕捉中)と
  理由表示で状態を確認し、成立を待ってから離陸する。どうしても飛ぶ場合のみ
  **「強制離陸」ボタン**(明示的 override。確認ダイアログつき)を使う —
  ヨー観測なしのコースト飛行になり得ることを理解して使うこと。
- **est_mode≠2(シャドー)**: ブロックせず**警告のみ**(コンソール+バッジ)。
  シャドー運用でも整列を確認してから飛ぶとログの価値が上がる。
- 磁気オートチューンカードの「ヨー観測融合」行に fused/停止・再捕捉
  (bit7)・直近 fused率(約5s窓)が出る。融合が成立しない場合は
  手回しテスト(機体 +30° 回頭で PC 表示 yaw_true が同方向・同量に動くか)
  と MoCap マッピング較正(§設定タブ)を確認する。
- ヨー基準を使わない飛行はソースを `off` にすればゲート・警告とも出ない。

## 14. 軌道モードの運用(Position: 円・直線往復・評価シーケンス)

1. 前提: Position モードで安定したホバリング(固定目標)ができていること。
2. 軌道セレクタで「円軌道」を選び、パラメータを入力する
   (制限は `control.json` の trajectory 節):
   中心 X/Y(±2.0m 以内)・半径(0.05–1.5m)・周期(3–120s)・
   回転方向(CW/CCW)・高度。初回は**半径 0.3m 程度・周期 20s 程度**の
   ゆっくりした円から。
3. **「円軌道開始」**: 現在位置から円周上の最近傍点へ滑らかに合流し、位相は
   その点から進む(MoCap が新鮮(0.3s 以内)でないと開始は拒否される)。
   XY プロットに目標軌道の円が重畳表示される。
4. **「停止(ホバ復帰)」**: その時点の軌道目標でホバリングに戻る(その場停止)。
   緊急時は通常どおり STOP / SPACE(即着陸)。
5. **「進行方向を向く」(face_tangent)**: ヨー角制御 ON のときのみ有効で、
   yaw_ref を接線方向に追従させる。接線ヨーの角速度は 360°/周期 であり、
   ヨースルーレート上限(45°/s)を超えないよう **周期 8 秒以上が必要**
   (8s 未満は開始が拒否される)。§13 Phase 1 を終えてから使うこと。
6. MoCap 途絶時は既存フェイルセーフと同一(300ms で水平化+軌道位相を凍結、
   2s で自動 STOP)。復帰時は位相が凍結時間ぶん補正され連続に進む。

### 14.1 直線往復(シャトル)軌道(2026-08-03 追加)

1. 軌道セレクタで「直線往復(シャトル)」を選び、パラメータを入力する:
   方向(X軸 0° / Y軸 90° / 角度指定)・中心 X/Y・振幅(0.05–0.5m)・
   周期(3–120s)・サイクル数(**0 = 連続**、手動停止まで)・高度。
2. ガード(`control.json` trajectory 節): 最大速度 2πA/T ≤ 0.5 m/s
   (`speed_max_mps`)、往復の両端点 center±A·e が ±0.5m
   (`excursion_abs_max_m`)以内。超えると開始が拒否される。
3. **「往復軌道開始」**: 現在位置を往復軸へ射影した点から滑らかに合流する
   (目標は center + A·sin(位相)·e の正弦往復)。XY プロットに往復線分が
   重畳表示される。
4. サイクル数 >0 のときは指定サイクル消化後、**次の端点(速度ゼロ点)で
   自動停止**しその端点でホバに復帰する。**「停止(ホバ復帰)」**は手動の
   即時停止(その時点の軌道目標でホバ)。MoCap 途絶時の位相凍結・復帰は
   円軌道と同一。

### 14.2 評価シーケンス(スクリプト軌道。2026-08-03 追加)

hover / circle / shuttle / yaw(その場回頭)セグメントの定型メニューを
1操作で流し、評価飛行(EKF2・移動ベースヨー等)の再現性を確保する。

1. プリセットは `control.json` の `trajectory.sequences`(既定
   `ekf2_eval_v1`: ホバ10s → 円 R0.35m 2周 → ホバ5s → X往復3回 →
   Y往復3回 → ヨー回頭 +90°→0→−90°→0 → ホバ10s)。UI にセグメント一覧と
   合計見積り秒が表示される。
2. **yaw セグメントを含むシーケンスはヨー角制御 ON が前提**(OFF では
   開始が拒否される — §13 Phase 1 を終えてから使うこと)。実行中に OFF に
   するとシーケンス時計ごと凍結し(盲目ランプ防止)、ON 復帰で連続再開する。
   全セグメントは開始前に円・往復と同じガードで一括検証され、**シーケンス内の
   circle には往復と同じ速度上限(周速 2πR/T ≤ 0.5 m/s)と可動域
   (|中心|+半径 ≤ ±0.5 m)も追加で課される**(単発の円軌道モードの制限値は
   従来どおり)。
3. 「このセグメントから開始」でバッテリ残量に応じて途中セグメントから
   実行できる(それより前は淡色表示でスキップ)。
4. **「シーケンス開始」**: 現在位置へ目標をスナップし、各セグメントは
   直前セグメントの終端から滑らかに合流して自動遷移する。合流点が現在
   目標から 0.05 m を超えて離れる遷移では、**0.25 m/s の等速直線で目標を
   運ぶ「移動中(トランジット)」小フェーズが自動挿入される**(目標の
   段差ジャンプを作らない。進行表示に反映され、残り時間見積りにも
   トランジット分が加算される)。実行中は進行(セグメント
   n/N・種別・残り秒)が表示され、全セグメント消化で最終目標のホバに
   自動復帰する。**「停止(ホバ復帰)」**で即時中断。
5. MoCap 途絶時はシーケンス時計ごと凍結(セグメント進行・ヨーランプも
   停止)し、復帰時は連続に再開する。2s で自動 STOP は既存どおり。
6. ログ記録中に開始すると、シーケンス定義・開始時刻が `*.meta.json` の
   `trajectory_sequence` に記録される(解析時の区間切り出し用。CSV の
   `traj_mode` 列は現セグメントの基礎モード 0/1/2 を報告する —
   LOG_STRUCTURE.md §11)。

## 15. 飛行後解析(flight_log_viewer)

1. 飛行時にログ保存トグルを ON にしておく(50Hz・v4 109列。列定義は
   [LOG_STRUCTURE.md](LOG_STRUCTURE.md)。旧ログ v1〜v3 もビューアで
   そのまま読める)。着陸後にトグル OFF でファイルが閉じられる。
2. 解析(初回は `flight_log_viewer/README.md` のセットアップで venv を作る):

   ```sh
   cd flight_log_viewer

   # 対話モード(出力内容とログを選ぶ)
   .venv/bin/python visualize.py

   # バッチ: 静止画グラフ+ヨー解析+サマリレポート
   .venv/bin/python visualize.py ../logs/flight_logs/20260706_120000_position.csv

   # アニメーション MP4(動画なし)/ すべて生成
   .venv/bin/python visualize.py ../logs/flight_logs/xxx.csv --animation
   .venv/bin/python visualize.py ../logs/flight_logs/xxx.csv --all

   # 2 ログのヨー安定性比較(FF あり/なし等の対照)
   .venv/bin/python visualize.py ../logs/flight_logs/a.csv --compare ../logs/flight_logs/b.csv
   ```

3. `output/<ログ名>/` に静止画(01〜20。データの無い図は自動スキップ)・
   `summary.txt`・`index.html`(統計+全グラフの HTML レポート)が生成される。
   ヨー評価で見るのは主に:
   - `10_yaw_comparison.png` — ヨー比較(Madgwick/EKF/指令。§13 Phase 0 の判定)
   - `12_ekf_diagnostics.png` — NIS・b_m・ΔB̂・ffg ゲートタイムライン
   - `14_yaw_tracking.png` — ヨー指令追従(PC 指令/機体適用目標/実測)
   - 系統別の RMS/最大誤差/ドリフト率 [°/min] は `summary.txt` の表
   姿勢制御の評価(v2.2: TLM_CTRL 由来)で見るのは主に:
   - `18_pid_ang_components.png` — 角度ループ PID 成分(P+I+D=指令角速度)
   - `19_pid_rate_components.png` — 角速度ループ PID 成分
   - `20_rate_tracking.png` — 指令角速度 vs 実測角速度の追従
   (いずれも `tlm_ctrl_flags` による無効区間 — 非飛行・ヨー制御 OFF — の
   網掛け付き)
4. スマホ動画と同期した合成アニメーションを作る場合は「ログ記録開始と同時に
   録画開始」しておき、`--video <動画> --track` を付ける(opencv-python 必要)。

## 16. 複数機モード(Multi)の運用

2〜4機を同一 MoCap 空間で同時に位置制御する(XY は各機とも機上XY制御
CMD_POS_ERR)。仕様は ARCHITECTURE.md「複数機モード」、ワイヤ仕様は
PROTOCOL.md が正。**複数機化のための機体ファーム改修はない**(多重化は
リレーとシリアル区間のみ)。ただし機体は機上XY制御(CMD_POS_ERR)対応
ビルドであること(§8.2.1 と同じ前提。旧ビルドは離陸後に自動着陸)。
スコープは静的目標のみ(円軌道なし)。CSV ログは機体ごとに記録され
(§15、LOG_STRUCTURE.md)、機体別ヨー角制御(±30° 制限)に対応する
(§16.2 の 6)。

### 16.1 前提(初回のみの準備)

1. **リレーの再書き込み(必須)**: 複数機対応はリレーファームの新機能。
   `~/.platformio/penv/bin/pio run -d firmware_relay -e release -t upload`
   で更新する(旧ファームのままだと「選択適用」がピア設定失敗になる)。
   UART は既定 **460800** になり、PC 側 `pc_server/config/server.json` の
   `serial.baudrate`(既定 460800)と**必ず一致**させる。
   **460800 が動かない USB シリアルブリッジ**では `-e release-115200` で
   書き込み、`serial.baudrate` を 115200 に戻す(**単機のみ推奨**。TLM_CTRL は
   リレー間引き(`multi.tlm_state_div`)の対象外のため、2機は間引きしても
   下り≈82% で余裕がない。PROTOCOL.md「帯域予算」)。
2. **wifi_channel の統一**: 同時に飛ばす機体は全機同じ `wifi_channel` で
   あること(リレーの無線は1チャネル。登録済み5機はすべて ch1)。
3. **Motive のリジッドボディ**: 機体ごとに1つのリジッドボディを作成し、
   streaming ID を割り当てる。**機体ごとにマーカー配置(形状)を変える**と
   ID の取り違え・入れ替わりを防げる(推奨)。
4. **rigid_body_id の設定**: Multi タブの**「リジッドボディ確認」**で観測中の
   ID と座標をライブ表示し、機体を1機ずつ動かしてどの ID がどの機体かを特定
   → ヘッダの機体プロファイル「編集」の **RB ID 列**に記入して保存する
   (未設定・重複のプロファイルは選択適用が拒否される)。

### 16.2 飛行手順

1. §1 の飛行前チェックリストを全機ぶん実施する。空間は機数に応じて広く
   (目標同士に 0.5m 以上の間隔を置ける広さ)。
2. 接続(§4〜5 と同じ)→ **Multi タブ**へ切替。
3. **機体選択(2〜4機)**にチェック → **「選択適用」**。リレーへ
   RLY_SET_PEERS が送られ、機体別ステータスチップに全機の状態が出る。
   失敗時はリレーファームが複数機対応版か確認する(§16.1 の 1)。
4. チップで**全機の機体リンク(テレメトリ)と MoCap(RB)が新鮮**である
   ことを確認する。
5. **機体別の目標 X/Y/Z** を設定する(XY は ±2.0m 以内。目標同士の XY 距離は
   **0.5m 以上** — 近すぎると一斉スタートが拒否され、飛行中の目標変更でも
   他機の目標との間隔が同様に検証される)。
6. (任意)**機体別のヨー角制御と FF プロファイル**: 各機体の行の
   「ヨー制御」チェック+ヨー目標で機体ごとに ON/OFF できる(OFF の機体は
   レートダンピングのみ)。**ヨー目標は ±30° に制限される** — XY 位置制御は
   制御座標系固定のため、大きなヨー保持は位置保持を劣化させる(主用途は
   ヨードリフトの打ち消し=0°保持)。MoCap 途絶中の機体へのヨー変更は
   拒否される。ヨー角制御を使う機体は、事前にその機体の較正+FF 適用
   (§12〜13)を済ませておくこと。FF は同じ行のセレクタ+「FF適用」で
   **機体別に適用できる**(全機が地上のときのみ受理。適用状態は行末に
   「FF: プロファイル名 … 機体:ff=…/EKF」と表示される)。
   **クイック較正(Attitude 0 / Yaw 0)も Multi モードのまま機体別に
   実行できる**(v2.2): 共通モニタ列のクイック較正カードのドロップダウンで
   対象機体を選んで押す(当該機が地上のときのみ受理。飛行中の機体は拒否)。
7. **一斉スタート**(確認ダイアログあり)。全機の目標設定・MoCap 鮮度・
   目標間隔・**地上にいること(z ≤ 0.3m — RB ID 取り違え対策)**が検証され、
   **1機でも不合格なら全機開始しない**。
8. 着陸は **STOP(全機着陸)または SPACE**。複数機モードでは常に
   **全機一斉**に停止する(機体単位の停止はスコープ外)。

### 16.3 安全規則(複数機固有)

- **SPACE / STOP は全機一斉**。1機の異常でも迷わず全機止める。
- **MoCap 途絶は機体ごと**: 当該機のみ 300ms で水平固定+警告、2s で
  CMD_STOP(自動着陸)。他機は飛行を継続するので、必要なら手動で全機 STOP。
- **XY 誤差の発散も機体ごと**: 飛行中に XY 位置誤差 1.0m 超が 1.0s 続いた
  機体は自動で CMD_STOP(自動着陸)+警告。rigid_body_id の取り違え
  (他機の位置で制御ループが閉じる)を疑い、「リジッドボディ確認」で照合し直す。
- **リンク喪失フェイルセーフは機体ごとに従来どおり**: セットポイント
  (CMD_POS_ERR)は機体ごと 50Hz で送られ、200ms 途絶で水平化、500ms で
  自律着陸(§9)。低電圧・OverG のフェイルセーフも機体ごとに単機と同一。
- **ID 入れ替わりを疑ったら即 SPACE**(マーカー形状が同一だと Motive 側で
  リジッドボディ ID が入れ替わることがある)。飛行前に「リジッドボディ確認」で
  機体を動かして照合しておく。
- **リレー再起動(電源瞬断・リセット)**: ピア設定は RAM のみのため消え、
  全機ぶんの上り(CMD_POS_ERR / CMD_STOP)がリレーで拒否される。各機は
  500ms のリンク喪失で自律着陸する(§9)。PC 側はテレメトリ途絶
  (既定 3s)を検出して当該スロットを解放し警告を出す。**復旧手順:
  切断 → 再接続 → 選択適用**(RLY_SET_PEERS の再設定)。
- **機体別ヨー角制御は単機 §13 と同じ前提**: EKF(est_mode=1)が不健全に
  なった機体は、その機体だけファーム側で自動的にレートダンピングへ縮退する
  (他機のヨー制御は継続)。縮退した機体は位置は保持するがヨーは流れるため、
  気になる場合はその機体のヨー制御を OFF にするか全機 STOP する。
